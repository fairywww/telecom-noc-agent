# 手写 Agent 循环

**范围说明**：本文基于 `agent.py` 与 `prompts/agent.txt` 的实现及一次真实运行记录。这是本仓库最核心的一篇笔记：不借助任何框架，Agent 的全部机制都在约 100 行代码里，每个环节都可指认。

## 1. 定义

本仓库对 Agent 的工作定义：**LLM + 工具 + 循环**。

- LLM 负责推理与决策（调不调工具、调哪个、数据够不够、结论是什么）；
- 工具是普通函数（本项目即 v0.2 的两个大屏接口）；
- 循环负责把两者粘起来：执行 LLM 要求的调用，把结果交还给它。

## 2. 循环结构

`agent.py` 的 `运行Agent()`，逻辑可压缩为：

```
messages = [system, user]
循环（最多 N 轮）:
    应答 = LLM(messages, tools)
    若 应答 无 tool_calls:
        返回 应答.content            # 终止条件①：模型给出最终答案
    把 应答（含 tool_calls）追加进 messages
    对每个 tool_call:
        结果 = 执行对应函数()
        把 {role:"tool", tool_call_id, content:结果} 追加进 messages
终止条件②：达到最大轮数，防止无限调用
```

两个终止条件缺一不可：①是正常出口，②是保护出口（模型可能反复调工具不收敛，每轮都在消耗 token 与时间）。

## 3. 消息结构：tool calling 的完整数据流

对话中共出现四种角色的消息：

| 角色 | 由谁产生 | 关键字段 |
|------|---------|---------|
| `system` | 调用方 | 行为规则 |
| `user` | 调用方 | 任务 |
| `assistant` | 模型 | `content` 或 `tool_calls`（含每个调用的 `id`、函数名、参数） |
| `tool` | 调用方 | `tool_call_id`（与请求配对）、`content`（工具返回的 JSON 字符串） |

一次真实运行中 `messages` 的演变（任务："全网状况如何，哪个地市最需要关注"）：

```
发送前2条:  [system, user]
第1轮模型返回: assistant, tool_calls=[查全网概览, 查地市退服明细]   ← 一轮可以要求多个调用
执行后追加3条: assistant(原样入史) + tool(概览结果) + tool(明细结果)
第2轮发送6条:  [system, user, assistant, tool, tool] → 模型返回纯 content，循环结束
```

`tool_call_id` 的作用：一轮有多个调用时，模型靠 id 把每份结果与自己的哪次请求对应起来。缺失或对不上会被服务端拒绝（400）。

## 4. State 就是 messages

聊天接口无状态（见 [02/llm-basics.md](../02-llm-api/llm-basics.md) 第 1 节），因此 **Agent 的全部记忆就是这份 messages 列表，每一轮都完整重发**。由此推论：

1. 轮数越多，重发的历史越长，token 消耗按轮数近似线性增长；
2. 工具返回的大 JSON 会一直留在历史里反复计费——生产系统需要压缩或裁剪历史（本项目留待阶段 5 评测时处理）。

## 5. 工具定义：LLM 只看得见说明书

`工具表` 中每个工具暴露给模型的只有 `name`、`description` 和参数 schema——模型看不见函数代码。因此 **description 的质量直接决定模型选工具的准确率**。本项目的写法把返回字段名也写进说明（如 `outage_total`），模型在答案中引用字段值时不会张冠李戴。

另一处细节：模型若要求调用不存在的工具，不抛异常中断，而是把 `{"error": "未知工具"}` 作为工具结果回填——让模型看到错误并自行纠正，循环得以继续。

## 6. 实测行为分析

本次运行中值得注意的三个现象：

1. **并行工具调用**：第 1 轮模型同时要求两个工具，而不是一轮一个——任务同时需要全局与明细数据，模型判断出两者无依赖关系；
2. **数字全部来自工具**：答案中的 41.8%（64/153）等占比是模型基于工具数据计算的，`prompts/agent.txt` 规则 1（禁止编造数字）生效；
3. **自发交叉校验**：模型主动验证"三地市合计 153 与全网总数一致"——未在提示词中要求，是模型自身的推理行为。
