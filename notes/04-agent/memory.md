# 多轮对话与记忆管理

**范围说明**：本文基于 `conversation.py`、`agent.py` 的历史参数改造与 `/api/agent/stream` 的会话接入。前置阅读：[agent-loop.md](agent-loop.md) 第 4 节（State 就是 messages）。

## 1. 问题：Agent 天生失忆

接口无状态，此前每次提问都从零开始——问完"苏州退服多少"再问"那南京呢"，模型不知道"那"指什么。多轮对话的本质只有一句话：**由调用方保存历史，下次请求时拼回 messages**。

## 2. 记忆结构：摘要 + 近期原文

`conversation.py` 的 `会话` 类维护两段记忆：

```
messages = [system] + [此前对话摘要(如有)] + [最近 N 轮问答原文] + [新问题]
```

| 部分 | 内容 | 成本特征 |
|------|------|---------|
| 滚动摘要 | 更早轮次经 LLM 压缩的一段话（≤150 字，保留地市/数字/结论） | 恒定 |
| 近期原文 | 最近 4 轮的问答对 | 有上限 |

超过保留轮数时，最早的轮次被并入摘要（`_压缩()`），摘要滚动更新。由此，**记忆的 token 成本不随对话轮数无限增长**——这是与"把全部历史原样重发"的关键区别。

## 3. 关键取舍：只记结论，不记工具中间量

每轮入史的只有「用户问题 + 最终答案」；该轮中的 tool_calls 与工具返回一律不留。理由：

1. 工具报文体积大（一次地市明细就数百 token），且其价值已凝结在答案里；
2. 旧的实时数据本身会过期，留着反而可能误导后续轮次。

实测验证：第二轮问"那南京呢？比刚才那个多多少？"——模型从上一轮**答案文本**中取得苏州 58 的数字完成对比（64 − 58 = 6），并标注"（前次查询）"。

## 4. 接入方式

- `运行Agent流()` 新增 `历史片段` 参数，插在 system 之后——循环本体不感知会话概念，职责仍然单一；
- `/api/agent/stream` 请求体新增可选 `session_id`：带上即启用记忆（服务端 `会话表` 按号存取），不带则保持无状态——**记忆是选配，不是强制**；
- 前端每次打开大屏生成一个随机会话号，页面生命周期即会话生命周期。

会话表目前是进程内字典：重启即失、多实例不共享。生产中会话存 Redis 等外部存储——这也是"代码与状态分离"的又一例。

## 5. 测试策略

`摘要生成()` 独立成模块级函数，测试中用 `monkeypatch` 替换为固定返回——压缩逻辑（截断、并入摘要、组装顺序）在零 LLM 依赖下可测。这延续了"慢而不稳定的部分与确定性逻辑分开测"的原则（见 [../01-python-fastapi/engineering.md](../01-python-fastapi/engineering.md) 第 4 节）。

## 6. 验证

```bash
python3 -m pytest tests/test_conversation.py -v          # 结构与压缩逻辑
printf "苏州现在退服多少个？\n那南京呢？比刚才那个多多少？\n" | python3 conversation.py
```

浏览器：连续两问（第二问用代词），观察第二问被正确解析。实测："无锡情况怎么样？"→"**它**在三个地市里排第几？"——"它"被正确解析为无锡。

## 自测

1. 为什么不把工具调用的中间报文存进会话历史？至少两个理由。
2. 滚动摘要会丢失细节。什么样的信息在摘要里最容易失真？提示词里为什么特别要求"保留地市、数字、结论"？
3. 把 `保留轮数` 从 4 改为 1，连续问 5 个相互关联的问题，第 5 问的回答质量会怎样变化？动手验证。
