# RAG 检索管线与 Agent 集成

**范围说明**：本文基于 `rag.py`、`data/knowledge/` 与 `agent.py` 中 `查运维知识` 工具的实现。核心内容：RAG 管线的四个环节、工具化 RAG 与固定管线的取舍、出处引用。

## 1. RAG 解决什么问题

LLM 的知识来自训练数据：有截止日期、不含私有资料（企业规范、内部流程）。RAG（Retrieval-Augmented Generation，检索增强生成）的思路是**先查后答**——从自有文档中检索相关片段，交给 LLM 作为答题依据。与微调相比：文档更新即知识更新、来源可追溯、成本低几个数量级；代价是每次回答多一步检索延迟。

## 2. 管线四环节（对应 rag.py）

```
Markdown 文档 → ① 切分 → ② 向量化 → ③ 索引 → ④ 检索
```

### ① 切分（`切分知识库()`）

按 `## 小节` 把文档切成块，块是检索的最小单位。粒度权衡：

| 块太大 | 块太小 |
|--------|--------|
| 一块混多个主题，检索排名失准 | 上下文残缺，命中了也答不全 |

本项目一个小节 3–8 行，一个主题一块，是手工文档的合理粒度。生产中对无结构长文常用"固定长度 + 重叠"切分。

### ② 向量化（`向量化()`）

Embedding 模型把文本映射为向量（本项目 Qwen3-Embedding-0.6B，1024 维，经 ModelScope API 调用，与 LLM 共用密钥）。语义相近的文本向量方向相近——这是整个 RAG 的数学基础。

实现细节：参与向量化的文本是 `来源·小节 + 正文` 拼接——标题中的关键词（如"处置流程"）对检索质量贡献很大。

### ③ 索引

本项目的"向量库"是一个 Python 列表。这是有意的选择：**几十个块的规模，线性扫描的余弦相似度就是完整、正确的检索**。FAISS/Milvus 解决的是百万级向量的检索速度与运维问题；`检索()` 的对外接口不依赖存储方式，规模上去时换底层实现即可。

### ④ 检索（`检索()`）

查询文本向量化 → 与所有块算余弦相似度 → 取 top-k（本项目 k=3）。实测："基站退服了应该按什么流程处理？"命中《基站退服处置流程·五步处置法》，相关度 0.882。

## 3. 两种 RAG 形态：固定管线 vs 工具化

| 形态 | 流程 | 适用 |
|------|------|------|
| 固定管线 | 每个问题都先检索再回答 | 纯知识问答产品 |
| 工具化（本项目） | 检索是 Agent 的一个工具，模型自主决定是否调用 | 混合任务：有的问题查数据，有的查知识 |

本项目选工具化的原因：问"苏州退服多少个"不需要也不应该检索知识库——模型会直接调数据接口。是否检索的判断交给模型，靠工具 description 里的一句话划界："回答制度、流程、定义类问题时使用；实时数字指标请用其他工具。"

## 4. 出处引用

两处配合实现可追溯：

1. 检索结果每块携带 `来源` 与 `小节` 字段；
2. `prompts/agent.txt` 规则 5 要求"引用知识库资料时注明出处"。

实测回答中出现"根据《基站退服处置流程·处置总则》"——运维场景中，**可追溯的回答才可采信**，这与工具调用轨迹（见 [tool-parameters.md](../04-agent/tool-parameters.md) 第 4 节）是同一设计目标。

## 5. 实测：数据与规范的协同推理

任务："南京现在退服全网最多，按照规范我下一步该怎么处置？"

```
第 1 轮：查运维知识(query=退服处置流程) → 命中处置总则、五步处置法
第 2 轮：查指定地市明细(city=南京)     → 64 站退服
第 3 轮：结论——64 站 > 批量退服标准 10 站，须立即上报并启动应急预案，
        随后按五步处置法执行（引用出处）
```

模型自主完成了"从规范中取阈值 → 用实时数据对照 → 得出处置动作"的推理链。这类**数据 + 制度的联合判断**正是运维 Agent 区别于普通问答机器人的核心价值。

## 6. 当前局限与升级路径

- 未设相关度阈值：即使问题与知识库完全无关，也会返回 top-3——生产中应设下限并允许"未检索到相关资料"；
- 无重排（rerank）环节：候选多时需要精排模型二次排序；
- 文档更新需重启进程重建索引；
- 规模化路径：文档增多 → 向量入 Milvus/FAISS；中文效果优化 → 对比 BGE 系列模型。

## 7. 验证

