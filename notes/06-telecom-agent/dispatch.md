# 事件驱动的智能调度与演示剧本引擎

**范围说明**：本文基于 v1.5 的实现：`noc_agent/dispatch.py`（调度器）、`noc_agent/server/noc_mock.py`（剧本引擎）、`noc_agent/storage/tickets.py`（建议单）与大屏调度台面板。核心问题：**系统如何从"人问机器答"升级为"告警来了机器主动动"，以及机器的权限边界画在哪。**

## 1. 从对话驱动到事件驱动

此前系统的全部智能行为由人的提问触发；调度场景要求反过来——告警产生时系统主动研判。实现为一条五段业务流，各段的责任主体刻意不同：

| 段 | 实现 | 责任主体 |
|----|------|---------|
| ① 感知 | 轮询告警接口，按「地市+传输环」归并为事件（告警压缩的最小实现） | 代码 |
| ② 研判 | 规则预筛（阈值判断）+ Agent 定界（根因推理，引用规范出处） | 代码 + 模型 |
| ③ 决策 | 生成「待确认」研判建议单；**人工确认后才转工单** | 模型建议，人拍板 |
| ④ 执行 | 建议单确认 → 复用既有工单链路（幂等、审计） | 代码 |
| ⑤ 闭环 | 恢复幕告警清除、指标回落；工单状态流转留待后续 | 代码 |

## 2. 规则与模型的分工原则

调度是写操作密集场景，判断必须分层：

- **确定性判断用代码**：「12 站 ≥ 10 站 → 批量退服 → 紧急/4 小时」写死在 `prescreen()`——毫秒级、零成本、永不出错，这类白纸黑字的规则不应消耗大模型；
- **模糊判断交模型**：「同环多站退服 + 光路 LOS → 更像传输中断还是电源问题」由 Agent 结合知识库定界，输出附规范出处；
- **终审权留给人**：建议单状态机（待确认 → 已确认/已否决）是审批门的数据模型落地，与写操作三道防线（见 [ticket-generation.md](ticket-generation.md)）叠加为第四道。

实测：风暴事件注入后，调度器自动产出建议单——预筛「紧急/限 4h（12 站 ≥ 10 站）」，Agent 定界「传输中断」并引用《基站退服常见原因·传输中断》的特征描述，与剧本注入的故障类型一致。

## 3. 幂等：轮询系统的生命线

调度器每 5 秒轮询一次，同一事件会被看到几十次。两层幂等保证不重复研判、不重复派单：

1. 事件键（`event_key` = 地市|传输环）在建议单表上唯一约束——同一事件只研判一次（研判是最贵的操作，一次数十秒与数千词元）；
2. 建议单确认走既有工单创建，继承「同地市待处理工单唯一」的存储层幂等。

## 4. 演示剧本引擎的设计

mock 数据的本质是**形真值假**：接口格式与真实系统一致，数值人造。v1.5 把静态 mock 升级为按剧本推进的状态机：

- **三幕剧**：平稳态 → 风暴（苏州传输环中断，12 站批量退服 + 光路 LOS 告警）→ 恢复（告警清除、指标回落）；指标接口与告警接口随幕联动；
- **导演遥控器**：`POST /api/scenario/next` / `reset`——演示节奏由讲者控制，不靠定时器；前端顶栏内置按钮；
- **剧本即测试夹具**：风暴幕的 12 站设定刻意越过批量退服阈值（10），使规则预筛、Agent 定界、审批门在一幕内全部被触发——一套剧本同时服务路演与自动化测试。

## 5. 彩排抓到的前端缺陷

演练时发现：建议单面板每 3 秒无条件重写 `innerHTML`，正要点击的按钮会被销毁导致点击丢失。修复：轮询结果与上次快照比对，**数据未变化不重绘**；用户操作后强制刷新。教训：带交互控件的轮询面板，重绘必须以数据变化为条件——这类缺陷只有全流程彩排能暴露，单元测试测不到。

## 6. 验证

```bash
# 三个终端：数据源(8001)、大屏后端(8002)、调度器
make run-noc && make run-adapter && python3 -m noc_agent.dispatch

curl -X POST localhost:8002/api/scenario/next   # 推进风暴幕（或点大屏"下一幕"）
# 约 30 秒后调度台出现建议单 → 点击"确认并派单" → 工单面板亮起
python3 -m pytest tests/test_dispatch.py -v      # 归并/预筛/审批门/幂等，零网络
```
