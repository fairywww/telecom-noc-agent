# 工单自动生成：写操作工具的安全设计

**范围说明**：本文基于 `tickets.py`（SQLite 存储）、`adapter.py` 的工单接口、`tools.py` 的 `创建处置工单` 工具与 `prompts/agent.txt` 规则 6。这是系统第一个**写操作**工具，也是「监控 → 诊断 → 派单」闭环的最后一环。

## 1. 读与写的分水岭

此前全部五个工具都是只读查询：调用一百次也不改变世界。写操作不同——每次调用都产生真实后果（一张工单、一次派单、一条通知）。因此写工具的设计重心从"查得准"变为"**不出事**"：误触发、重复触发、无审计是三类典型事故。

Agent 系统的能力演进顺序应当是：先让它看（查询），再让它说（建议），最后才让它做（操作）——每一级的信任都由上一级的可追溯性挣来。

## 2. 三道防线

| 防线 | 位置 | 实现 |
|------|------|------|
| 意图门 | 提示词（agent.txt 规则 6） | 仅在用户明确要求（"建单/派单"）时调用；建单前先查数据与规范 |
| 幂等保护 | 存储层（tickets.py） | 同地市已有「待处理」工单即拒绝，返回已有单号 |
| 审计字段 | 数据模型 | 每张工单记录创建时间与来源（agent / manual） |

**防线位置的原则：越硬的保证放越深的层**。提示词是软约束（模型可能失守），所以防重复不靠提示词，靠存储层的查询判断——即使模型连调十次，库里也只有一张单。

### 实测三连

1. 问"南京现在情况怎么样？"——只查询，未建单（意图门生效）；
2. 说"请按规范给南京建一张处置工单"——Agent 先查地市明细、再查处置规范，然后才调用建单工具，工单内容自带关键数字（64 站、41.8%）与规范依据（《基站退服处置流程》）；
3. 再说"再给南京建一张"——存储层拒绝并返回已有单号，Agent 如实转达且建议"跟进现有工单"（错误是数据原则的又一次应用）。

## 3. 存储：SQLite

工单用 SQLite（Python 标准库自带）持久化，进程重启不丢。要点：

- 建表语句 `CREATE TABLE IF NOT EXISTS` 使模块首次使用时自建库，无需初始化步骤；
- 幂等检查与插入在同一连接中完成；
- **运行期数据不进代码库**：`data/tickets.db` 已加入 `.gitignore`——代码（人人相同）与数据（各环境各异）分离，与 `.env` 的道理一致。

## 4. 端到端闭环

大屏左下新增「处置工单」面板，5 秒轮询 `GET /api/tickets`。至此四个面板全部接通真实链路，黑灯运维的完整故事在一块屏上可见：

```
监控（KPI/地市分布） → 诊断（右栏 Agent 对话） → 派单（工单面板实时出现）
```

在右栏要求 Agent 建单，数秒后工单出现在左栏——写操作的结果对用户即时可见，这本身也是一种审计。

## 5. 局限与后续

- 工单尚无状态流转（待处理 → 处理中 → 已销障）与关单接口；
- 高危写操作的**人工审批门**（Agent 提交草稿、人确认后生效）未实现——生产环境必备，LangGraph 的 human-in-the-loop 中断点正对应此需求（见 [../04-agent/langgraph-comparison.md](../04-agent/langgraph-comparison.md) 第 3 节）；
- 幂等键目前是"地市 + 待处理状态"，真实系统通常用调用方生成的唯一请求号（request id）。
