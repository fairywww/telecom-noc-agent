# Agent 评测

**范围说明**：本文基于 `eval.py` 与 `agent.py` 的词元统计改造。核心问题：**LLM 输出不确定，如何量化"这次改动让 Agent 变好了还是变坏了"。**

## 1. 为什么 Agent 需要专门的评测

普通代码用单元测试断言精确输出；LLM 每次输出都不同，无法逐字断言。但"不确定"不等于"不可测"——把断言从"输出等于什么"放宽为"输出**必须包含**什么"，就得到可自动判定的回归测试。

评测集与单元测试分工明确：

| | tests/（pytest） | eval.py |
|--|-----------------|---------|
| 测什么 | 确定性逻辑（聚合、契约、切分） | 端到端智能行为 |
| 依赖 | 无网络、无 LLM | 需要服务与 LLM |
| 速度 | 1.6 秒 | 约半分钟一题 |
| 何时跑 | 每次改代码 | 改提示词/模型/工具描述后 |

## 2. 评测集设计

每个用例 = 问题 + 必含关键词。四个用例各覆盖一类能力：

1. 全网数字（须调数据工具且数字正确：153）；
2. 排名判断（须比较明细：南京）；
3. 知识问答（须调知识库：四个等级名称）；
4. 数据+规范联合（须取阈值 10 并给出应急预案动作）。

关键词判定粗糙但零成本、无歧义。进阶方案是"LLM 当裁判"（用另一个模型给答案打分），在关键词无法表达判定标准（如"语气是否专业"）时才值得引入。

## 3. 四个指标

| 指标 | 含义 | 本次实测（修复后） |
|------|------|------------------|
| 成功率 | 通过用例占比 | 4/4 |
| 平均轮数 | 循环执行的轮次 | 2.0 |
| 平均耗时 | 单题端到端秒数 | 8.5 秒 |
| 词元合计 | 所有轮次 `usage.total_tokens` 之和 | 8025 |

词元统计的实现：每轮应答的 `usage.total_tokens` 累加。由于历史逐轮完整重发，**轮数增长时词元按近似平方增长**——这个数字是 Agent 成本优化的第一观测点。

## 4. 评测的第一战果：抓到一个复现缺陷

首轮评测 3/4：第 3 题遇到服务端"返回 200 但 `choices` 为空"。此前一次同样现象被当作偶发；评测证明它是**可复现问题**。处置：

1. `运行Agent()` 对空应答自动重试（最多 3 次），连续失败才报错；
2. 重跑评测回归：4/4 通过。

这就是评测的价值闭环：**量化 → 暴露 → 修复 → 回归确认**。没有评测集，这类间歇性缺陷只会在演示现场随机爆发。

## 5. 使用方式

```bash
python3 eval.py    # 需要 8001/8002 两个服务在运行
```

改动提示词（prompts/）、更换模型（.env 的 LLM_MODEL）、修改工具描述后重跑，对比四个指标的变化。
