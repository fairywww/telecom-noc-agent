# 新增一个指标：三层改动与前后端契约

**范围说明**：本文基于 v0.2 中"告警总数"指标的接入过程，涉及 `noc_agent/server/noc_mock.py`、`noc_agent/server/adapter.py`、`web/index.html` 三个文件。目标是回答一个通用问题：**大屏上要多显示一个数字，系统里要动哪些地方，为什么是这些地方。**

## 1. 结论先行

一个指标从产生到显示，经过三层，每层各改一处：

| 层 | 文件 | 本次改动 | 职责 |
|----|------|---------|------|
| 数据层 | `noc_agent/server/noc_mock.py` | 每个专业数据中增加 `alarm_count` 字段 | 提供原始数据 |
| 适配层 | `noc_agent/server/adapter.py` | 聚合 `alarm_count`，应答中增加 `alarm_total` 字段 | 原始数据 → 前端可用格式 |
| 展示层 | `web/index.html` | 将 `alarm_total` 填入 `id="告警数"` 的元素 | 取数、填入页面 |

三层通过 HTTP 接口衔接，互相只依赖**字段名**，不依赖对方的内部实现。

## 2. 数据层：字段扩展

`noc_agent/server/noc_mock.py` 第 18–22 行，在每个专业的数据字典中并列增加一个键：

```python
"南京": {"4G": {"outage_count": 40, "alarm_count": 120}, ...}
```

要点：原始数据按「地市 → 专业 → 指标」三级嵌套组织。新增指标只是在最内层字典里加一个键值对，不改变结构，因此不影响既有读取方。

## 3. 适配层：聚合逻辑的函数化

### 3.1 改动内容

`noc_agent/server/adapter.py` 原先只对 `outage_count` 加总，加总逻辑内联写在路由函数中。本次将其抽取为独立函数（`noc_agent/server/adapter.py` 第 24–34 行）：

```python
def aggregate(行, 字段名):
    return sum(
        专业数据[字段名]
        for 各专业 in 行.values()          # 遍历每个地市
        for 专业数据 in 各专业.values()     # 遍历 4G/5G
    )
```

路由函数中新增指标由此变为一次调用：

```python
return {
    "outage_total": aggregate(行, "outage_count"),
    "alarm_total": aggregate(行, "alarm_count"),
    "city_count": len(行),
}
```

### 3.2 为什么抽函数（DRY 原则）

退服与告警的加总逻辑完全相同，只有字段名不同。若复制粘贴循环代码，将来每加一个指标就多一份重复代码；一旦聚合口径调整（例如排除某地市），需要修改所有副本，漏改即产生不一致。将差异部分（字段名）参数化、公共部分收拢为一个函数后，新增指标的成本降为一行，口径调整只改一处。这一原则称为 DRY（Don't Repeat Yourself）。

### 3.3 生成器表达式

`sum(...)` 内部是一个双重循环的生成器表达式，等价于：

```python
总 = 0
for 各专业 in 行.values():        # {"4G": {...}, "5G": {...}}
    for 专业数据 in 各专业.values():   # {"outage_count": 40, "alarm_count": 120}
        总 += 专业数据[字段名]
```

生成器表达式逐项产生数值交给 `sum`，不构建中间列表。

## 4. 前后端契约与向后兼容

适配层应答中的字段名（`outage_total`、`alarm_total`、`city_count`）是前后端之间的**契约**：前端按名取值，后端保证名称与含义稳定。

变更契约时需区分两类操作：

| 操作 | 性质 | 影响 |
|------|------|------|
| 新增字段 | 非破坏性（向后兼容） | 旧前端忽略新字段，照常工作 |
| 改名 / 删除 / 改变含义 | 破坏性 | 所有按旧名取值的前端立即失效 |

本次是新增 `alarm_total`，属于非破坏性变更，因此可以先改后端、后改前端，两步之间系统始终可用。生产系统的接口演进普遍遵循「只加不改」的原则，原因即在于此。

命名一致性也属于契约的一部分：`alarm_total` 沿用了 `outage_total` 的 `<指标>_total` 命名模式，前端开发者可以据此预期后续字段的形态。

## 5. 分层验证方法

链路跨三层时，从数据源头逐层向外验证，每层只确认本层的产出，出错时可立即定位在哪一层：

| 步骤 | 验证点 | 预期 |
|------|--------|------|
| 1 | `http://localhost:8001/api/statistics/all` | 每个专业数据中出现 `alarm_count` |
| 2 | `http://localhost:8002/api/kpi` | 应答中出现 `"alarm_total": 477` |
| 3 | `http://localhost:8002/` 页面 | 告警总数格显示 477 |

其中 477 = 120 + 86 + 95 + 71 + 63 + 42，与数据层手工求和一致，证明聚合逻辑正确。

注意：uvicorn 默认不监视代码变更，修改 `.py` 文件后需重启服务才生效（开发期可使用 `--reload` 参数开启自动重载）；`web/index.html` 由静态文件托管，刷新浏览器即生效。
